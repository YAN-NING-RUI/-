# FreeRTOS 与 I²C 调试笔记

记录 STM32F103 项目中的 I²C 驱动选择、RAM 布局，以及任务和传感器初始化的排查思路。整理自《freertos系统的一些总结.md》。

## I²C 驱动怎么选

| 实现方式 | 调用任务如何等待 | 适用场景 |
| --- | --- | --- |
| GPIO 软件 I²C，轮询或延时 | 调用任务在传输结束前保持在函数中，期间仍可能被更高优先级任务抢占 | 短事务、低频访问、便于直接观察时序 |
| 硬件 I²C，HAL 轮询 | I²C 外设生成时序，调用任务轮询状态，等待完成或超时 | 初始化和简单调试 |
| 硬件 I²C，中断或 DMA | 启动传输后可继续执行，或阻塞在任务通知上等待完成。示例 API 为 `HAL_I2C_Mem_Write_IT` 和 `HAL_I2C_Mem_Write_DMA` | 希望减少忙等，或让其他任务并行处理 |
| 软件 I²C，定时器驱动状态机 | 定时器事件驱动状态推进，SDA 方向、ACK 和总线条件由状态机处理 | 缺少可用硬件 I²C，且能验证中断延迟和完整时序 |

在 FreeRTOS 中，轮询和忙等占用**调用任务的执行时间**。能否切换到其他任务取决于调度策略、任务优先级，以及是否处在关中断或调度被暂停的区间。中断与 DMA 的取舍要看事务长度、触发频率和驱动复杂度。原记录针对手头 F1 项目倾向软件方案，遇到硬件 I²C 异常时，应先按具体型号、硅片修订版和复现条件核对 ST 勘误。

### 软件 I²C 的时序边界

- 普通 I²C 的 SCL、SDA 使用开漏或开集电极加上拉。上拉阻值依据总线电容、允许的上升时间和器件灌电流选取，4.7 kΩ 是常见起点。
- 正常数据位在 SCL 低电平时更新 SDA，在 SCL 高电平时保持稳定。START 和 STOP 通过 SCL 为高时的 SDA 跳变表示。
- 100 kHz 对应 10 µs 周期。高低各 5 µs 是理想 50% 占空比的例子。设计还须满足所用速率模式的最小高低时间、建立保持时间与上升时间。
- 定时器可以提供节拍。完整状态机还需处理 START、重复 START、STOP、ACK/NACK，按设备要求处理时钟拉伸。若目标设备能拉低 SCL，释放 SCL 后应读取实际电平，再推进高电平阶段。

[I²C 时序与上拉计算 · NXP UM10204](https://www.nxp.com/docs/en/user-guide/UM10204.pdf)

## STM32F103 的 RAM 预算

| 型号 | Flash | SRAM |
| --- | --- | --- |
| STM32F103C8T6 | 64 KiB | 20 KiB |
| STM32F103CBT6 | 128 KiB | 20 KiB |

SRAM 常用于 `.data`、`.bss`、栈、堆和项目自定义段，具体位置看链接脚本和 `.map` 文件。零初始化的静态串口缓冲区通常位于 `.bss`。动态创建任务时，任务栈通常从 FreeRTOS 的分配器获得空间，静态创建任务时由调用者提供栈缓冲区。核算时检查所选的 `heap_*.c` 和实际分配路径，避免重复统计堆中的任务栈。

## 项目现象与排查顺序

### 定时器服务任务和 Wi-Fi 任务疑似没有执行

1. 在调用 `vTaskStartScheduler()` 前后做低成本日志或 GPIO 标记，确认执行到调度器，并检查任务创建返回值、句柄、剩余堆和堆分配失败钩子。
2. 分别记录任务入口和等待事件前后。入口标记未出现时查任务创建、调度器启动和高优先级任务是否持续占用 CPU。入口已出现时再查事件组的置位方、等待掩码和超时。
3. 如果 `xTimerManagerTask` 指软件定时器相关任务或回调，核对 `configUSE_TIMERS`、任务优先级、软件定时器创建和启动返回值，再检查回调是否曾运行。以项目实际符号为准。

### SGP30 和 DHT11 初始化进入 handle_error

给每个初始化步骤记录设备、失败点和返回码，先定位哪一步进入 `handle_error`。SGP30 检查 I²C 地址、ACK、供电和命令时序。DHT11 检查独立的数据线、上拉和脉宽采样时序。先单独复现每个设备，再组合运行。原记录只确认进入错误处理，根因待实测。

### 对硬件交互选择合适的观测方式

在中断或时序敏感的外设代码中停住内核，可能改变中断响应、总线时序和 FIFO 占用。先用计数器、缓冲日志、GPIO 脉冲或逻辑分析仪记录事件，再在故障状态稳定、停机影响可控的位置设置断点。
