# FDCAN Message RAM 与收发中断

先区分数据帧与远程帧，再从过滤器接受报文开始，跟踪 FIFO、NVIC、HAL 回调和 FreeRTOS 队列。Message RAM 的区域规划以 FDCAN 配置为准。

## 数据帧与远程帧的区别 {#data-vs-remote}

**数据帧用于传递数据；远程帧用于请求其他节点发送对应的数据帧。** STM32H743 的 FDCAN 是外设名称，支持经典 CAN 与 CAN FD。经典 CAN 数据帧最多携带 8 字节，CAN FD 数据帧最多携带 64 字节。远程帧属于经典 CAN，**CAN FD 没有远程帧**；CAN FD 需要请求与响应时，由应用协议用数据帧约定请求内容。 [ST · AN5348 协议概述](https://www.st.com/content/st_com/en/technical-documents/an5348-introduction-to-fdcan-peripherals-for-stm32-mcus-stmicroelectronics.html)

### 经典 CAN 帧对照 {#classic-frame-comparison}

| 比较项 | 数据帧（Data Frame） | 远程帧（Remote Frame） |
| --- | --- | --- |
| 用途 | 发布测量值、状态或命令等应用数据 | 请求某个 CAN ID 对应的数据 |
| RTR 位 | `0`，显性 | `1`，隐性 |
| 数据字段 | 可携带 0～8 字节 | 无数据字段，实际负载始终为 0 字节 |
| DLC 含义 | 描述本帧的数据长度；常规经典 CAN 使用 0～8 | 描述请求的数据长度，应与对应响应数据帧的 DLC 一致 |
| ID 格式 | 支持 11 位标准 ID 或 29 位扩展 ID | 同样支持两种 ID 格式 |
| HAL 发送帧类型 | `FDCAN_DATA_FRAME` | `FDCAN_REMOTE_FRAME` |
| HAL 接收判别 | `hdr.RxFrameType == FDCAN_DATA_FRAME` | `hdr.RxFrameType == FDCAN_REMOTE_FRAME` |

这里的 0/1 表示总线逻辑位，不能直接当作 CANH 或 CANL 的对地电压。标准帧/扩展帧区分 ID 长度，数据帧/远程帧区分用途，两组分类相互独立。DLC 为 0 的数据帧仍是数据帧，应通过 RTR / `RxFrameType` 判断帧类型。 [CiA · 经典 CAN 帧格式](https://can-cia.org/can-knowledge/can-cc)

由 RTR 的取值和显性覆盖隐性的规则可推导：**不同节点同时发送相同 ID、相同 ID 格式的数据帧和远程帧时，数据帧在 RTR 位赢得总线仲裁。** 这个结论要求 ID 与格式都相同，不能泛化成所有数据帧都比所有远程帧优先。 [CiA · RTR 与显性/隐性定义](https://www.can-cia.org/fileadmin/cia/documents/brochures/can_dictionary_v13_2026.pdf)

### 请求、响应与 ACK {#remote-request-response}

假设应用约定：标准 ID `0x123` 对应一个 4 字节的状态量，并由节点 B 提供。

```text
节点 A → 总线：远程帧，标准 ID=0x123，RTR=1，DLC=4，无数据字段
节点 B → 总线：数据帧，标准 ID=0x123，RTR=0，DLC=4，Data=11 22 33 44
```

远程帧中的 `DLC=4` 表示请求 4 字节，远程帧本身携带的数据为 0 字节。响应沿用请求的 ID 与 ID 格式；CAN ID 表示应用约定的消息含义，并非协议固定的节点地址。数据帧也可以由节点主动发送，无需先收到远程请求。 [CiA · 远程帧定义](https://www.can-cia.org/fileadmin/cia/documents/brochures/can_dictionary_v13_2026.pdf)

**STM32H743 的 FDCAN 不支持收到远程帧后由硬件自动发送响应数据帧。** 应用需要读取请求、判断 ID 与 DLC、准备数据，再提交发送；RTOS 工程可把请求交给工作任务处理。总线 ACK 只确认帧被其他节点正确接收，不能据此确认业务响应已产生。 [ST · RM0433，FDCAN Normal operation](https://www.st.com/resource/en/reference_manual/rm0433-stm32h742-stm32h743753-and-stm32h750-value-line-advanced-armbased-32bit-mcus-stmicroelectronics.pdf)

## Message RAM 布局 {#ram}

FDCAN 的过滤表、收发 FIFO、接收缓冲区和发送事件 FIFO 存在专用 Message RAM 布局中。这些配置定义的是内存结构，而不是 CAN 线上数据帧的长度。

| CubeIDE 字段 | 示例值 | 作用与注意点 |
| --- | --- | --- |
| `Message RAM Offset` | 0 | 该 FDCAN 实例在共享 Message RAM 中的起始偏移；FDCAN1/2 区域不得重叠。 |
| `Std Filters Nbr` | 1 | 预留 1 个标准 ID 过滤元素；需要再调用 HAL 配置过滤规则。 |
| `Ext Filters Nbr` | 0 | 不预留扩展 ID 过滤元素。 |
| `Rx FIFO0 Elmts Nbr` | 4 | FIFO0 可缓存最多 4 条未取走的接收报文；不是 4 Byte。 |
| `Rx FIFO0 Elmt Size` | 8 bytes | 每个元素的数据字段容量为 8 字节，适合 Classic CAN；另外还要存头部元数据。 |
| `Rx FIFO1 Elmts Nbr` | 0 | 暂不使用第二个接收 FIFO。 |
| `Rx Buffers Nbr` | 0 | 不使用专用接收 Buffer。 |
| `Tx Events Nbr` | 0 | 不记录发送事件 FIFO；发送事件本身与发送完成中断不同。 |
| `Tx Buffers Nbr` | 0 | 不用专用发送 Buffer。 |
| `Tx FIFO/Queue Elmts Nbr` | 4 | 为待发送报文预留 4 个元素。 |
| `Tx FIFO/Queue Mode` | FIFO | 按发送 FIFO 机制管理待发送请求；与 Queue 模式的选择有别。 |
| `Tx Elmt Size` | 8 bytes | 每个发送元素承载最多 8 字节数据字段。 |

### 计算 Message RAM 占用

以标准 ID 过滤器 ×1、Rx FIFO0 ×4（每元素 8B header + 8B data）、Tx FIFO ×4（同样 16B）为例：

```text
标准 ID Filter  : 1 ×  4B =   4B
Rx FIFO0       : 4 × 16B =  64B
Tx FIFO        : 4 × 16B =  64B
--------------------------------
合计（此示例）：           132B = 33 个 32-bit word
```

这是仅对已配置区域进行的基本内存布局计算，不代表当前整个 FDCAN 子系统只有 132B RAM，也不替代实际生成代码对双 FDCAN 共享布局的验证。

### 过滤器与 FIFO {#filters}

收到完整 CAN 帧（ID / 帧类型 / DLC / 数据帧的可选负载） → 过滤规则（决定接受及投递位置） → Rx FIFO0 / FIFO1（排队等待 CPU 读取）

以下示例预先给 `StdFiltersNbr` 至少分配 1 个元素，再用 `HAL_FDCAN_ConfigFilter()` 写入第 0 条标准 ID 过滤规则。

```c
FDCAN_FilterTypeDef filter = {
    .IdType = FDCAN_STANDARD_ID,
    .FilterIndex = 0U,
    .FilterType = FDCAN_FILTER_MASK,
    .FilterConfig = FDCAN_FILTER_TO_RXFIFO0,
    .FilterID1 = 0x123U,
    .FilterID2 = 0x7FFU
};
```

- `FilterIndex` 选择过滤表槽位。标准表的索引受 `StdFiltersNbr` 限制，重配同一槽位会替换该规则。
- 掩码模式按 `(receivedId & mask) == (filterId & mask)` 匹配。这里 `receivedId` 是收到的 ID，`filterId` 来自 `FilterID1`，`mask` 来自 `FilterID2`。`0x7FF` 比较全部 11 位，精确匹配 `0x123`。
- `FDCAN_FILTER_TO_RXFIFO0` 选择接收 FIFO，具体元素位置由硬件队列管理。`RxBufferIndex` 和 `IsCalibrationMsg` 用于专用接收缓冲区配置，此处可省略。
- 要只接收指定 ID 的数据帧，通过 `HAL_FDCAN_ConfigGlobalFilter()` 拒绝不匹配的标准帧和扩展帧，同时拒绝远程帧。接收远程请求时，按下面的小节调整全局策略。

### 远程帧的全局过滤策略 {#remote-filter}

沿用上面的标准 ID `0x123` 精确匹配规则。若应用只需要数据帧，在 `HAL_FDCAN_Init()` 之后、`HAL_FDCAN_Start()` 之前配置：

```c
if (HAL_FDCAN_ConfigGlobalFilter(
        &hfdcan1,
        FDCAN_REJECT,        /* 拒绝未匹配的标准 ID */
        FDCAN_REJECT,        /* 拒绝未匹配的扩展 ID */
        FDCAN_REJECT_REMOTE, /* 拒绝标准 ID 远程帧 */
        FDCAN_REJECT_REMOTE  /* 拒绝扩展 ID 远程帧 */
    ) != HAL_OK) {
    Error_Handler();
}
```

需要接收标准 ID 远程请求时，把第 4 个实参改为 `FDCAN_FILTER_REMOTE`，让标准远程帧继续按 ID 规则过滤；第 5 个实参控制扩展远程帧。`FDCAN_FILTER_REMOTE` 不会无条件接收所有远程帧。本例中仅 ID `0x123` 的标准数据帧和标准远程帧可进入 FIFO0，其他 ID 仍被拒绝。 [ST STM32H7 HAL · 全局过滤接口与宏](https://github.com/STMicroelectronics/stm32h7xx-hal-driver/blob/master/Inc/stm32h7xx_hal_fdcan.h)

## 发送报文头与提交结果 {#tx-header}

下面构造 ID 为 `0x123`、负载为 8 字节的经典 CAN 标准数据帧。将 `txHeader` 和实际的 8 字节负载一同传给驱动。

```c
FDCAN_TxHeaderTypeDef txHeader = {
    .Identifier = 0x123U,
    .IdType = FDCAN_STANDARD_ID,
    .TxFrameType = FDCAN_DATA_FRAME,
    .DataLength = FDCAN_DLC_BYTES_8,
    .ErrorStateIndicator = FDCAN_ESI_ACTIVE,
    .BitRateSwitch = FDCAN_BRS_OFF,
    .FDFormat = FDCAN_CLASSIC_CAN,
    .TxEventFifoControl = FDCAN_NO_TX_EVENTS,
    .MessageMarker = 0U
};
```

| 字段 | 示例的含义 |
| --- | --- |
| `Identifier`、`IdType` | 11 位标准 ID |
| `TxFrameType` | 数据帧 |
| `DataLength` | 数据长度编码 DLC，按项目 HAL 的宏填写，避免硬编码数值 |
| `FDFormat`、`ErrorStateIndicator`、`BitRateSwitch` | 经典 CAN 整帧使用 Nominal 位时序，线上没有 CAN FD 的 ESI 或 BRS 字段 |
| `TxEventFifoControl`、`MessageMarker` | 不向 Tx Event FIFO 写入事件记录，本例无需关联标记 |

`HAL_FDCAN_AddMessageToTxFifoQ()` 返回 `HAL_OK` 表示请求已提交，硬件随后进行仲裁和发送。要确认结果，观察相应发送完成状态或通知，并结合错误状态和外部节点抓包验证。若应用封装（例如 `S2_Transmit()`）返回 HAL 提交状态，应检查它以便处理队列满等提交失败。

[ST STM32H7 HAL · FDCAN 类型与字段](https://github.com/STMicroelectronics/stm32h7xx-hal-driver/blob/master/Inc/stm32h7xx_hal_fdcan.h)

### 用 HAL 发送远程请求 {#remote-tx-header}

沿用上面的 `txHeader`，改为请求标准 ID `0x123` 的 4 字节数据。示例要求已配置发送 FIFO 和至少 8 字节的发送元素，并已启动控制器：

```c
FDCAN_TxHeaderTypeDef requestHeader = txHeader;
uint8_t unusedData[8] = {0};

requestHeader.TxFrameType = FDCAN_REMOTE_FRAME;
requestHeader.DataLength = FDCAN_DLC_BYTES_4; /* 期望响应的长度 */
requestHeader.FDFormat = FDCAN_CLASSIC_CAN;
requestHeader.BitRateSwitch = FDCAN_BRS_OFF;

if (HAL_FDCAN_AddMessageToTxFifoQ(
        &hfdcan1, &requestHeader, unusedData) != HAL_OK) {
    Error_Handler();
}
```

`unusedData` 为 HAL 的内存拷贝提供有效缓冲，数组内容不会作为远程帧的数据字段发送。所核对的 H7 HAL 实现会按 DLC 从 `pTxData` 拷贝，即使帧类型为远程帧；因此示例使用 8 字节数组，避免传 `NULL` 或容量不足的数组。具体拷贝要求以工程内的 HAL 版本为准。 [ST STM32H7 HAL · FDCAN_CopyMessageToRAM](https://github.com/STMicroelectronics/stm32h7xx-hal-driver/blob/master/Src/stm32h7xx_hal_fdcan.c)

### 接收与网关转发时保留帧类型 {#remote-rx-forwarding}

`HAL_FDCAN_GetRxMessage()` 返回后先检查 `hdr.RxFrameType`：远程帧的有效负载长度为 0，`hdr.DataLength` 保留请求长度的 DLC；数据帧才按 DLC 解析负载。HAL 可能按 DLC 向接收数组拷贝 Message RAM 内容，远程帧对应数组中的字节不能当成收到的业务数据。接收数组仍须满足 HAL 的缓冲要求。

透明转发时，软件队列应保留 ID、`IdType`、帧类型、原始 DLC、`FDFormat` 与 `BitRateSwitch`；数据帧另存有效负载。将接收头转换为发送头时，把 `RxFrameType` 映射到 `TxFrameType`，远程帧继续以经典 CAN 远程帧转发。若只保存 ID 与负载长度，会丢失远程请求中的 DLC 含义。本文后面的 `CAN_OnReceive(id, data, len)` 接口仅适用于数据负载分发，远程请求应另行处理或扩展参数。 [ST STM32H7 HAL · 接收头与发送头定义](https://github.com/STMicroelectronics/stm32h7xx-hal-driver/blob/master/Inc/stm32h7xx_hal_fdcan.h)

## FIFO 中断与 FreeRTOS 接收链路 {#irq}

### NVIC 中断线路

| 配置项 | 含义 | 初期建议 |
| --- | --- | --- |
| `FDCAN1 interrupt 0` | FDCAN1 的第 0 条中断线路；可承载 FIFO0 收到报文等事件 | 启用 |
| `FDCAN1 interrupt 1` | 同一个 FDCAN1 的第 1 条中断线路，允许单独映射其他事件 | 先关闭 |
| `FDCAN calibration unit interrupt` | FDCAN 时钟校准单元相关，不是每收一帧必须开的中断 | 先关闭 |

**注意：**这两条 `interrupt 0/1` 不是 FDCAN1/FDCAN2。你可以把不同事件映射到不同中断线路，但现在不必复杂化。

报文被放入 Rx FIFO0（FDCAN 硬件） → 控制器事件标志（NEW_MESSAGE / WATERMARK / FULL） → NVIC IT0（进入 ISR） → HAL 回调（GetRxMessage 取走数据） → FreeRTOS 队列（网关任务后续处理）

### 启用接收中断

1. **NVIC 启用：**CubeIDE 中勾选 `FDCAN1 interrupt 0`，生成 `FDCAN1_IT0_IRQHandler()`。
2. **控制器通知启用：**`HAL_FDCAN_ActivateNotification(&hfdcan1, FDCAN_IT_RX_FIFO0_NEW_MESSAGE, 0)`。
3. **回调与 FIFO 读取：**在 `HAL_FDCAN_RxFifo0Callback()` 内，通过 `HAL_FDCAN_GetRxMessage()` 从 FIFO 取走报文。

### FIFO0 中断演示 {#fifo-demo}

假设 FIFO 深度为 4 帧。切换中断条件后逐帧接收，观察事件在何时产生。

<FdcanFifo />

| 事件 | 什么时候触发 | 是否适合实时网关 |
| --- | --- | --- |
| `FDCAN_IT_RX_FIFO0_NEW_MESSAGE` | 每有一条新报文进入 FIFO 时设置事件标志 | 推荐 |
| `FDCAN_IT_RX_FIFO0_WATERMARK` | FIFO 占用到达你配置的阈值时触发 | 可用于批处理；单帧可能等待下一帧 |
| `FDCAN_IT_RX_FIFO0_FULL` | 4 个元素都被占用时触发 | 适合预警，不能作为低延迟主接收机制 |
| `FDCAN_IT_RX_FIFO0_MESSAGE_LOST` | 由于 FIFO 条件等原因丢失接收报文 | 建议监测 |

**默认水位不是 1：**硬件水位字段为 0 时，水位中断禁用。你的 FIFO 深度设为 4 只代表缓存能力，不会自动变成“第 4 条才中断”；是否每条通知取决于你启用的事件。

### H7 HAL 最小调用关系（示意）

```c
/* 先由 CubeMX 完成 MX_FDCAN1_Init() */
/* 随后配置接收 Filter / GlobalFilter：本节省略具体规则 */

HAL_FDCAN_ActivateNotification(
    &hfdcan1, FDCAN_IT_RX_FIFO0_NEW_MESSAGE, 0);
HAL_FDCAN_Start(&hfdcan1);

/* Core/Src/stm32h7xx_it.c 通常由 CubeMX 生成 */
void FDCAN1_IT0_IRQHandler(void)
{
    HAL_FDCAN_IRQHandler(&hfdcan1);
}

/* 用户代码：收到报文后从 FIFO 取走 */
void HAL_FDCAN_RxFifo0Callback(FDCAN_HandleTypeDef *hfdcan,
                                uint32_t it)
{
    if (hfdcan->Instance != FDCAN1 ||
        !(it & FDCAN_IT_RX_FIFO0_NEW_MESSAGE)) return;

    FDCAN_RxHeaderTypeDef hdr;
    uint8_t data[8];
    while (HAL_FDCAN_GetRxFifoFillLevel(hfdcan,
                                        FDCAN_RX_FIFO0) > 0U) {
        if (HAL_FDCAN_GetRxMessage(hfdcan,
                                   FDCAN_RX_FIFO0,
                                   &hdr, data) != HAL_OK) break;
        /* 按 hdr.RxFrameType 区分远程请求和数据负载 */
        /* 复制报文头及有效负载到用户结构；发送到 FreeRTOS 队列 */
    }
}
```

:::tip 要点
**重要：**这是逻辑骨架，不是直接可编译的整套工程；实际还需配置 Filter / GlobalFilter、完整错误检查和任务队列。使用 `xQueueSendFromISR()` 时，要保证 ISR 优先级符合 FreeRTOS 限制。
:::

### FreeRTOS 中断优先级

STM32 NVIC 中较小的优先级数值代表较高抢占优先级。你截图里的 Preemption Priority = 5，是否适合在回调中调用 `xQueueSendFromISR()`，取决于 `FreeRTOSConfig.h` 中的 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`。在常见配置下，允许调用 FreeRTOS ISR API 的中断数值应不小于该阈值（并须匹配优先级位数与分组）。

中断回调只做**快速取帧、复制结构、入队、必要时请求任务切换**；ID 过滤后的路由策略、统计和发送由 FreeRTOS 任务完成。不要在 ISR 中执行长时间等待、阻塞式打印或重计算。

## 应用层接收回调 {#application-rx-callback}

HAL 用 `HAL_FDCAN_RxFifo0Callback()` 通知 FIFO0 接收事件。在上述中断链路中，该回调由 `HAL_FDCAN_IRQHandler()` 触发，执行时仍处于 ISR。应用层可以另外定义自己的接收接口，让 CAN 工作任务在出队后选择转发、解析或记录报文。 [ST STM32H7 HAL · FDCAN 驱动源码](https://github.com/STMicroelectronics/stm32h7xx-hal-driver/blob/master/Src/stm32h7xx_hal_fdcan.c)

```text
FDCAN IRQ → HAL FIFO0 回调取帧 → 报文按值入队
CAN 工作任务出队 → CAN_OnReceive() → 当前注册的处理函数
```

### 注册和分发 {#register-rx-callback}

```c
#include <stddef.h>
#include <stdint.h>

typedef void (*CanRxCallback_t)(uint32_t id,
                                const uint8_t *data,
                                uint8_t len);

static CanRxCallback_t rxCallback = NULL;

void CAN_RegisterCallback(CanRxCallback_t callback)
{
    rxCallback = callback;
}

void CAN_OnReceive(uint32_t id, const uint8_t *data, uint8_t len)
{
    CanRxCallback_t callback = rxCallback;
    if (callback != NULL && (data != NULL || len == 0U)) {
        callback(id, data, len);
    }
}
```

这里的 `CAN_RegisterCallback()` 和 `CAN_OnReceive()` 由应用自行实现。`CanRxCallback_t` 约定参数与返回值；文件作用域的 `static` 变量 `rxCallback` 用来保存地址，具有内部链接，整个程序运行期间有效。调用 `CAN_RegisterCallback(MyCanHandler)` 保存兼容的处理函数地址。工作任务执行 `CAN_OnReceive()` 时才调用该函数。业务始终固定时，直接调用处理函数也很清楚。

若网关要按模式切换，可由工作任务注册 `CAN_Forward` 或 `CAN_Log`。指针赋值的语义见 [运行时切换函数指针](../../固件基础/C语言对象指针与函数指针.md#switch-function-target)。上述示例要求事先约定注册与调用的同步策略，详见 [FreeRTOS 回调切换与队列交接](../../实时系统/FreeRTOS任务与内存排查.md#callback-handoff)。

### 接收报文的长度与生命周期 {#rx-payload-lifetime}

- `len` 是有效负载字节数。先按帧格式、帧类型和当前 HAL 的 DLC 表示取得长度，再检查缓冲容量。经典 CAN 数据帧负载最多 8 字节，CAN FD 最多 64 字节；远程帧不携带有效负载。接收缓冲区要在调用 `HAL_FDCAN_GetRxMessage()` 前按所接收的帧和 HAL 写入要求分配。
- `const uint8_t *data` 表示处理函数通过该指针只读，数据的生命周期由缓冲区决定。工作任务可以把当前报文的负载数组借给回调。处理函数若要在返回后继续使用，应复制有效负载或接管由协议明确管理的缓冲区。
