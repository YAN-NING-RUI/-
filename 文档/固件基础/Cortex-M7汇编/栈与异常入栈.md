# Cortex-M7 栈与异常入栈

从 PUSH 和 POP 的地址变化开始，区分普通函数栈帧、异常现场和工程中的 MSP、PSP 配置。

## PUSH、POP 与函数栈帧 {#push-pop}

### 满递减栈的地址变化

`PUSH` 只是在**当前 SP 指向的 RAM 栈**里保存寄存器的数值。Cortex-M7 常用的栈模型是**满递减栈（Full Descending）**：压栈时地址向低处增长。

假设起始：

```text
SP = 0x20001000
R4 = 10, R5 = 20, LR = 0x08001235
```

执行：

```asm
PUSH {R4, R5, LR}
```

之后：

```text
较高地址
0x20001000    原 SP 位置（未由该 PUSH 写入）
0x20000FFC    LR = 0x08001235
0x20000FF8    R5 = 20
0x20000FF4    R4 = 10        <-- 新 SP
较低地址
```

一次 `PUSH` 保存三个 32 位字，共 12 字节。计算式为 `新 SP = 旧 SP − 寄存器数 × 4 字节`，因此新 SP 为 `0x20000FF4`。**低编号寄存器保存在较低地址**，排列规则由架构确定，不是汇编文本中的任意逐条执行顺序。

### 临时压栈与恢复顺序

```asm
PUSH {R4, R5, LR}   @ SP = 0x20000FF4
PUSH {R6}           @ SP = 0x20000FF0（新增 R6 在更低地址）
POP  {R6}           @ SP = 0x20000FF4（恢复到原栈顶）
POP  {R4, R5, PC}   @ 恢复 R4/R5，原 LR 的值被装入 PC，返回
```

关键是：**先进入栈的数据不被后来的压栈移动或打乱**；后压的数据占用更低地址，必须先释放，SP 才能重新指向原来的 R4。

错误示例：

```asm
PUSH {R4, R5, LR}
PUSH {R6}
POP  {R4, R5, PC}   @ 错误：SP 仍指向 R6
```

这不会让 CPU 自动“查找以前的 R4”。它只会从当前 SP 起的连续位置取值，导致寄存器错位，写入 PC 时甚至可能跳转到错误地址并触发异常。

> `POP` 后，相应 SRAM 字节中的旧内容可能仍留在物理内存里，但这些字节在**逻辑上**不再属于当前已占用的栈帧。

### 函数栈帧的分配与释放

下面是展示函数入口/出口的简化示意，20 字节空间只是示例：

```asm
my_function:
    PUSH {R4, R5, LR}     @ 保留寄存器；SP -= 12
    SUB  SP, SP, #20      @ 为局部变量/对齐预留空间；SP -= 20

    @ 函数主体，可能有其他运算和调用

    ADD  SP, SP, #20      @ 释放局部变量空间
    POP  {R4, R5, PC}    @ 恢复寄存器，并返回
```

如果进入时 SP 为 8 字节对齐，`12 + 20 = 32` 字节，调用边界仍可维持 8 字节对齐。实际函数会根据 ABI、优化和栈布局选择不同序言（prologue）/尾声（epilogue）。

**要点**：普通函数的栈帧不是“每个寄存器一块专用 SRAM”，而是当前任务/线程所使用的栈中的连续区域。

## MSP、PSP 与异常现场 {#exception-stack}

Cortex-M7 有两套栈指针：

- **MSP（Main Stack Pointer）**：复位后默认的主栈；异常处理在 Handler mode 下使用 MSP。
- **PSP（Process Stack Pointer）**：可在 Thread mode 下选择；FreeRTOS 任务通常使用 PSP。

汇编指令 `PUSH`/`POP` 使用的是**当前生效的 SP**，而不是某块写死的 SRAM。

异常入口把硬件异常帧压入被打断上下文当时使用的栈。若 Thread mode 选用 PSP，异常帧落在 PSP，随后处理程序在 Handler mode 使用 MSP。若被打断时使用 MSP，异常帧落在 MSP。基本帧保存 R0–R3、R12、LR、返回 PC 和 xPSR；对齐填充、浮点扩展帧与惰性保存由配置和现场决定。异常返回时，处理程序的 LR 中的 `EXC_RETURN` 编码指定恢复路径。

## 把初始 MSP 放到 DTCM {#dtcm-stack}

以 [STM32H743 存储映射](../STM32H743存储映射.md) 中的 128 KiB DTCM 为例，这个可写区域可作为主栈或分配器管理的内存。

```text
DTCM 有效地址范围：0x20000000 ~ 0x2001FFFF
DTCM 末尾后一个地址：0x20020000
```

栈向低地址增长，因此可令**初始 SP** 位于末尾后一地址（前提是这片区域已合理分配，不和其他数据冲突）：

```text
/* 仅示意 .ld 的局部设置 */
MEMORY {
    DTCMRAM (xrw) : ORIGIN = 0x20000000, LENGTH = 128K
}
_estack = ORIGIN(DTCMRAM) + LENGTH(DTCMRAM); /* 0x20020000 */
```

典型 Cortex-M 启动向量表的第一个字存放初始 MSP：

```asm
.word _estack
.word Reset_Handler
```

若 SP 初值为 `0x20020000`，执行 `PUSH {R4, R5, LR}` 后：

```text
SP = 0x2001FFF4
R4 保存到 0x2001FFF4
R5 保存到 0x2001FFF8
LR 保存到 0x2001FFFC
```

**重要边界**：

- `_estack` 指定栈顶地址，**并不自动保证**整个 DTCM 都保留给栈，也不负责检测堆栈碰撞。
- 堆（Heap）是由内存分配器管理的区域，不是 SP 的另一种叫法；`malloc()` 的堆空间取决于链接脚本和 `_sbrk` / 运行库实现。FreeRTOS 的动态内存方案另有自己的分配机制。
- SP 可以指向 DTCM，也可以指向其他合法、可写、满足栈对齐和访问权限的 SRAM 区域；`PUSH`/`POP` 本身不关心底层 RAM 块名字。

查看 [链接脚本与启动初始化](../链接脚本与启动初始化.md) 追踪链接符号和复位入口。任务栈空间与堆用量见 [FreeRTOS 任务与内存排查](../../实时系统/FreeRTOS任务与内存排查.md)。
