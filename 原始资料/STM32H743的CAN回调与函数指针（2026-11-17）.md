# STM32H743 嵌入式学习笔记（二）：CAN 回调机制与函数指针的运行时切换

> 整理范围：上一份 Markdown 笔记生成之后的两组问题——CAN 回调代码的设计思路；函数指针能否在程序运行期间更换目标。
>
> 核心结论：**函数的机器代码通常在编译、链接阶段确定；函数指针变量保存的目标地址可以在运行时改变。回调将“事件发生”与“具体处理动作”解耦。**

## 一、先理解整体设计

设想 CAN 驱动模块收到一条报文。驱动知道**何时收到、收到什么**，但不应该必须知道上层业务要**转发、记录还是解析**。

回调机制的流程是：

1. 上层定义一个满足约定参数与返回值类型的处理函数。
2. 上层调用 `CAN_RegisterCallback(处理函数名)`，将其**函数地址**交给 CAN 模块。
3. CAN 模块把地址保存在函数指针变量中。
4. 收到报文时，CAN 模块通过该函数指针调用上层处理函数。

```text
上层业务层                             CAN 接收模块
MyCanHandler()  ── 注册函数地址 ───────> rxCallback
                                            │
CAN 总线收到数据 ──> CAN_OnReceive() ────────┘
                                            │
                                 rxCallback(id, data)
                                            │
                                    执行 MyCanHandler()
```

核心是**注册时传地址，事件发生时才调用函数**。

## 二、按代码执行过程逐行拆解

原始示例：

```c
/* 1. 定义回调函数指针“类型”，不是变量 */
typedef void (*CanRxCallback_t)(
    uint32_t id,
    const uint8_t *data
);

/* 2. 定义一个保存回调地址的函数指针变量 */
static CanRxCallback_t rxCallback = NULL;

/* 3. 注册：保存调用者传入的函数地址 */
void CAN_RegisterCallback(CanRxCallback_t callback)
{
    rxCallback = callback;
}

/* 4. 收到报文时分发 */
void CAN_OnReceive(uint32_t id, const uint8_t *data)
{
    if (rxCallback != NULL)
    {
        rxCallback(id, data);
    }
}
```

### 1. `typedef void (*CanRxCallback_t)(...)`

这定义**函数指针类型** `CanRxCallback_t`。能被它指向的函数必须有匹配的函数原型：返回 `void`，参数依次为 `uint32_t`、`const uint8_t *`。

```c
void MyCanHandler(uint32_t id, const uint8_t *data)
{
    /* 处理业务数据 */
}

CanRxCallback_t handler = MyCanHandler;  /* 函数指针变量 */
```

比较：

```c
void MyCanHandler(uint32_t id, const uint8_t *data); /* 函数声明 */
CanRxCallback_t handler;                             /* 函数指针变量 */
```

### 2. `static CanRxCallback_t rxCallback = NULL;`

- `rxCallback`：真正保存函数地址的变量。
- `NULL`：尚未注册任何处理函数，调用前须检查。
- `static`：这里假定它写在 `.c` 文件的**文件作用域**，含义是内部链接，只能在当前源文件按名称直接访问；变量在整个程序运行期间存在。若写在函数内部，`static` 的作用域语义不同。

### 3. `CAN_RegisterCallback()`：保存函数地址，并不调用函数

```c
CAN_RegisterCallback(MyCanHandler);   /* 注册，传入函数地址 */
```

进入注册函数后，执行：

```c
rxCallback = callback;
```

此时 `rxCallback` 指向 `MyCanHandler`。要区分以下两种表达式：

```c
MyCanHandler           /* 指代函数，作为实参时可转换为函数指针 */
MyCanHandler(id, data) /* 立即调用函数 */
```

### 4. `CAN_OnReceive()`：事件发生后间接调用

```c
if (rxCallback != NULL)
{
    rxCallback(id, data);
}
```

如果先前注册的是 `MyCanHandler`，那么上述调用的实际效果相当于：

```c
MyCanHandler(id, data);
```

但 **`CAN_OnReceive()` 本身无需知道业务函数的具体名称**；它只依赖统一的函数签名。

## 三、函数指针能否在程序运行时改变？

**可以。** 注册不是编译器指令，而是普通的运行时赋值操作。只要程序执行新的注册操作，函数指针变量就能指向另一个同类型函数。

```c
void CAN_Forward(uint32_t id, const uint8_t *data)
{
    /* 转发逻辑 */
}

void CAN_Log(uint32_t id, const uint8_t *data)
{
    /* 记录逻辑 */
}

void SetCanMode(uint8_t mode)
{
    if (mode == 0U)
    {
        CAN_RegisterCallback(CAN_Forward);
    }
    else
    {
        CAN_RegisterCallback(CAN_Log);
    }
}
```

执行过程：

```text
启动时：rxCallback = NULL
模式 0：rxCallback = CAN_Forward 的入口地址
模式 1：rxCallback = CAN_Log 的入口地址
收到报文：调用 rxCallback 当前指向的函数
```

**改变的是 SRAM 中函数指针变量保存的目标，不是重写 Flash 里的函数机器码。** 一般情况下只能在程序已经包含的函数之间切换；若要加载新代码，需要独立的代码加载／Flash 编程机制。

## 四、为什么不直接调用业务函数？

直接调用：

```c
void CAN_OnReceive(uint32_t id, const uint8_t *data)
{
    MyCanHandler(id, data);
}
```

这样简单、清晰，**固定业务场景完全可用**。但它使 CAN 模块直接依赖 `MyCanHandler`。

采用回调以后：

- CAN 模块只知道统一的 `CanRxCallback_t` 接口。
- 上层可以选择转发、解析、记录等不同处理函数。
- CAN 模块不必随着上层业务函数名称或实现的变化而改动。

这就是**解耦**。函数指针不保证性能更高；间接调用有时比直接调用更难内联优化。不要为“用了函数指针”而在简单模块里过度设计。

## 五、放到 STM32H743 + FreeRTOS 工程，需要注意的事项

### 1. 中断上下文与任务上下文

如果在 `HAL_FDCAN_RxFifo0Callback()` 中直接调用 `CAN_OnReceive()`，业务回调也在**中断上下文**执行。此时不宜做长时间报文解析、阻塞等待或调用不支持 ISR 的 RTOS API。

更稳妥的较复杂网关设计是：

```text
FDCAN 收到报文
    ↓
FDCAN Rx FIFO 中断
    ↓
HAL_FDCAN_GetRxMessage() 取出报文
    ↓
将 ID、DLC、数据复制进 FreeRTOS 消息队列（使用 ISR 适用接口）
    ↓
CAN 工作任务取出消息
    ↓
CAN_OnReceive() → 业务处理函数
```

这样把中断中的快速收包与任务中的业务处理分离。

### 2. 运行时更换回调时的并发问题

如果某个任务更新 `rxCallback`，另一个任务或 ISR 同时调用它，可能出现竞争条件。以下写法只减少一次调用中的重复读取：

```c
void CAN_OnReceive(uint32_t id, const uint8_t *data)
{
    CanRxCallback_t cb = rxCallback;
    if (cb != NULL)
    {
        cb(id, data);
    }
}
```

**这段代码本身并不保证并发安全**。实际工程应考虑临界区、原子访问、任务间消息传递或由单个任务统一管理回调。`volatile` 不是完整的同步机制。

最简单可靠的方式：**在启动 FDCAN 中断或相关任务之前注册一次回调，运行期间不更换。**

### 3. 不要保留指向临时接收缓冲区的裸指针

`const uint8_t *data` 只表示不能通过该指针修改数据，不表示数据一直有效。例如 `data` 可能指向 HAL 接收处理函数中的局部数组。如果业务要稍后处理，应把有效载荷复制到自身缓冲区或队列。

另外，原示例没有携带数据长度，真实 CAN 项目应明确 DLC 与有效载荷长度，避免将所有报文默认视为 8 字节。

## 六、一个更实用的回调接口形式

```c
typedef void (*CanRxCallback_t)(
    uint32_t id,
    const uint8_t *data,
    uint8_t len
);

static CanRxCallback_t rxCallback = NULL;

void CAN_RegisterCallback(CanRxCallback_t callback)
{
    rxCallback = callback;
}

void CAN_OnReceive(uint32_t id, const uint8_t *data, uint8_t len)
{
    /* 前提：回调只在约定的安全上下文中调用；并发修改另行同步 */
    CanRxCallback_t cb = rxCallback;

    if ((cb != NULL) && (data != NULL))
    {
        cb(id, data, len);
    }
}

void MyCanHandler(uint32_t id, const uint8_t *data, uint8_t len)
{
    /* 根据 id 和 len 处理数据，不越界访问 data */
    (void)id;
    (void)data;
    (void)len;
}

/* 系统初始化阶段 */
/* CAN_RegisterCallback(MyCanHandler); */
```

这个简化示例用于理解接口机制。真实工程应进一步根据 **Classic CAN/CAN FD、DLC 解析、缓冲区长度、错误处理、调用上下文和并发策略** 完善。

## 七、精简记忆卡片

| 概念 | 一句话理解 |
|---|---|
| 函数 | 可执行的代码逻辑 |
| 函数指针变量 | 保存要调用哪个函数的地址 |
| 函数指针类型 `typedef` | 约定可指向函数的参数和返回值形式 |
| 注册回调 | 把函数地址写入某个函数指针变量 |
| 执行回调 | 事件发生时，通过保存的地址间接调用函数 |
| 运行时切换 | 通过再次赋值，改为指向另一个兼容函数 |
| 模块解耦 | 驱动知道“何时调用”，业务决定“具体做什么” |
| 并发安全 | 多任务或 ISR 读写回调时必须考虑同步 |

**最重要的区分：** `CAN_RegisterCallback(MyCanHandler)` 是保存函数地址；`MyCanHandler(id, data)` 是直接执行函数；`rxCallback(id, data)` 是通过已保存的函数地址间接执行函数。

---

**适用场景：** STM32H743、CMSIS-RTOS2 / FreeRTOS、FDCAN 接收事件回调、通用嵌入式驱动接口。  
**结论置信度：** C 语言函数指针语义极高；具体 RTOS 同步策略需结合中断优先级、调用上下文和 HAL 实现确定。
