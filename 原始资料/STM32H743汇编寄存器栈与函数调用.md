# STM32H743：ARM 汇编、寄存器、栈与函数调用机制

> **适用对象**：STM32H743（ARM Cortex-M7，Armv7E-M / Thumb-2）、STM32CubeIDE + GNU Arm GCC。  
> **整理范围**：在《STM32H743 存储体系与 Cache》笔记之后的问答，重点回答：`LDR` 到底谁装入谁、`[]` / `{}` 是什么、`PUSH` 与 `POP` 如何配对、SP 能否指向 DTCM、16 个核心寄存器的职责、Caller-saved / Callee-saved、R0 的返回值如何避免覆盖。  
> **阅读目标**：能看懂常见 C 函数在 `Disassembly` 中的执行流程，分清 CPU 寄存器、RAM 栈和函数调用规范。

## 0. 先建立四个基本观念

1. **CPU 寄存器不是 SRAM 中的变量**。R0～R15 是 Cortex-M7 内核中程序可见的 32 位寄存器；`PUSH` 时才把寄存器当前的数值复制到 SP 指向的 RAM 栈中。
2. **汇编指令与 C 代码不是“一行对一行”**。编译器根据优化等级、调用约定和可用寄存器生成指令。同一段 C 代码在 `-O0` 和 `-O2` 下可能明显不同。
3. **普通 Thumb-2 汇编一般把目标寄存器写在前面**。例如 `ADD R0, R1, R2` 的效果是 `R0 = R1 + R2`，而 `STR` 的第一操作数是源数据、第二操作数是存储器目标，需要看清指令本身的语义。
4. **函数调用的寄存器保存规则主要是软件 ABI 约定，不是 `BL` 自动完成**。除了异常入栈这种独立的硬件机制，普通函数是否压栈、何时恢复，由编译器或汇编程序安排。

## 1. 常见 Thumb-2 汇编指令速查

STM32H743 使用 Cortex-M7 的 Thumb / Thumb-2 指令编码，而不是 x86 汇编。下表是阅读 HAL 驱动、寄存器代码和 C 函数反汇编时的优先学习内容。

### 1.1 数据读写与栈

| 指令 | 典型示例 | 含义 |
| --- | --- | --- |
| `MOV` | `MOV R0, R1` | 把 R1 的值复制到 R0，不访问普通内存 |
| `LDR` | `LDR R0, [R1]` | 从 R1 指向的地址读取 32 位数据，存入 R0 |
| `STR` | `STR R0, [R1]` | 把 R0 的 32 位值写入 R1 指向的地址 |
| `LDRB` / `STRB` | `LDRB R0, [R1]` | 读取 / 写入 8 位数据 |
| `LDRH` / `STRH` | `LDRH R0, [R1]` | 读取 / 写入 16 位数据 |
| `PUSH` | `PUSH {R4, LR}` | 将一组寄存器的值保存到当前栈 |
| `POP` | `POP {R4, PC}` | 从当前栈恢复一组寄存器，写入 PC 可返回 / 跳转 |

### 1.2 算术与位操作

| 指令 | 典型含义 | C 语言近似表达 |
| --- | --- | --- |
| `ADD` / `SUB` | 加法 / 减法 | `a + b` / `a - b` |
| `MUL` | 整数乘法 | `a * b` |
| `SDIV` / `UDIV` | 有符号 / 无符号整数除法 | `a / b` |
| `AND` / `ORR` / `EOR` | 按位与 / 或 / 异或 | `&` / `\|` / `^` |
| `BIC` | 按掩码清零位 | `a & ~mask` |
| `LSL` / `LSR` / `ASR` | 左移 / 逻辑右移 / 算术右移 | `<<`，以及不同语义的右移 |
| `UXTB` / `SXTB` | 提取低 8 位并零扩展 / 符号扩展 | 协议字节、带符号数据处理 |
| `REV` | 反转 32 位数的字节顺序 | 大小端转换 |

### 1.3 比较、跳转与特殊指令

| 指令 | 作用 |
| --- | --- |
| `CMP` | 比较操作数，更新条件标志（不保存减法结果） |
| `TST` | 按位与测试，更新条件标志 |
| `B` | 无条件跳转 |
| `BEQ` / `BNE` | Z 标志指示相等 / 不相等时跳转 |
| `BGT` / `BLT` | 有符号大于 / 小于时跳转 |
| `CBZ` / `CBNZ` | 寄存器为零 / 非零时跳转 |
| `BL` | 跳转调用函数，并更新 LR（返回位置） |
| `BX LR` | 按 LR 的值进行分支，常用于普通函数返回 |
| `MRS` / `MSR` | 读 / 写特殊寄存器，如 PRIMASK、CONTROL |
| `CPSID i` / `CPSIE i` | 禁止 / 允许可配置优先级中断；并非屏蔽所有异常 |
| `DMB` / `DSB` / `ISB` | 内存顺序 / 同步 / 指令流屏障 |
| `WFI` / `NOP` | 等待中断 / 空操作 |
| `LDREX` / `STREX` | 独占访存，常用于同步原语 |

> **易错点**：`MOV` 是寄存器传值；`LDR` 是读取内存；`STR` 是写入内存。`LDR R0, =0x12345678` 中的 `=` 属于汇编器的加载常量伪指令形式，不保证一定对应一条物理机器指令。

## 2. 谁装入谁？`[]`、`{}`、`#` 分别是什么

### 2.1 `LDR R0, [R1]` 的精确语义

假设：

```text
CPU 中：
  R1 = 0x20000000
  R0 = 0

DTCM RAM 中：
  地址 0x20000000 保存着 32 位整数 100
```

执行：

```asm
LDR R0, [R1]
```

结果：

```text
R0 = 100
R1 = 0x20000000（不变）
RAM[0x20000000] = 100（不变）
```

- **`R0`**：读取结果的目的寄存器。
- **`R1`**：保存目标内存地址。
- **`[R1]`**：访问 R1 中的地址所指向的内存，而**不是**读取 R1 本身。

对比：

```asm
MOV R0, R1         ; R0 = R1，复制地址数值本身
LDR R0, [R1]       ; R0 = RAM[R1]，读取内存内容
STR R0, [R1]       ; RAM[R1] = R0，写入内存内容
LDR R0, [R1, #4]   ; R0 = RAM[R1+4]，地址偏移 4 字节
```

若 R1 = `0x20000000`，最后一条访问的是 `0x20000004`，不是“第 4 个 `uint32_t` 元素”。

### 2.2 常见符号对照

| 符号 | 例子 | 作用 |
| --- | --- | --- |
| `[]` | `[R1]` | 表示内存寻址；也可包含基址与偏移量 |
| `{}` | `{R4, R5, LR}` | 表示寄存器**列表**，常见于 `PUSH` / `POP` |
| `#` | `#10` | 立即数，表示字面整数 10 |
| `!` | `[R1, #4]!` | 地址写回：执行寻址时更新基址寄存器 |
| `=` | `LDR R0, =0x12345678` | 汇编器加载常数的伪指令语法 |
| `,` | `ADD R0, R1, R2` | 分隔操作数 |

> 注意：汇编的 `{R4, R5}` **不是** C 语言的代码块花括号，而是“寄存器集合”；`[R1]` 也不能简单理解成 C 数组下标，它表示按地址访问内存。

## 3. Cortex-M7 的 16 个核心寄存器分别做什么

| 寄存器 | 典型职责 | 返回后的保留规则 |
| --- | --- | --- |
| **R0** | 第 1 个整数/指针参数；常见的 32 位返回值 | Caller-saved |
| **R1** | 第 2 个参数；部分 64 位返回值使用 R0:R1 | Caller-saved |
| **R2** | 第 3 个参数、临时值 | Caller-saved |
| **R3** | 第 4 个参数、临时值 | Caller-saved |
| **R4～R8** | 保存调用后仍然需要的通用数据 | Callee-saved |
| **R9** | 平台约定用途，或额外的被调用者保存通用寄存器 | 平台相关（见第 5 节） |
| **R10～R11** | 被调用者保存寄存器；R11 在某些工具链中也作帧指针 | Callee-saved |
| **R12** | 临时寄存器（IP），也用于链接器辅助代码 | Caller-saved |
| **R13 / SP** | 当前栈指针，指向当前栈顶 | 调用边界应按约定恢复 |
| **R14 / LR** | 链接寄存器：普通调用的返回位置；异常时具有其他特殊含义 | 调用其他函数可能覆盖 LR |
| **R15 / PC** | 程序计数器：控制执行位置 | 专用程序控制寄存器 |

### 3.1 R0～R3：传参和返回值

```c
int add(int a, int b) { return a + b; }
```

典型的高度简化汇编：

```asm
add:
    ADD R0, R0, R1    ; 输入 a 通常在 R0，b 在 R1；结果写回 R0
    BX  LR            ; 返回调用者
```

对于普通 32 位整数参数，前四个一般按 R0～R3 传递；剩余参数通常使用栈。实际还受参数类型、对齐、结构体、浮点 ABI 等因素影响。

### 3.2 R4～R11：不是“固定变量寄存器”

这些寄存器**没有硬件固定的业务含义**。编译器可以把循环计数、指针、中间数据放入它们。它们之所以特别，是因为通用函数调用规范要求被调用函数保留其中大部分寄存器的原值；只要要修改，就需要在返回前恢复。

### 3.3 SP：当前栈指针；实际存在 MSP 和 PSP

Cortex-M7 有两套栈指针：

- **MSP（Main Stack Pointer）**：复位后默认的主栈；异常处理在 Handler mode 下使用 MSP。
- **PSP（Process Stack Pointer）**：可在 Thread mode 下选择；FreeRTOS 任务通常使用 PSP。

汇编指令 `PUSH`/`POP` 使用的是**当前生效的 SP**，而不是某块写死的 SRAM。

### 3.4 LR 与 PC：函数如何返回

```asm
A:
    BL B          ; LR 被设置为返回到 A 中下一条执行位置
    ; B 返回后继续执行

B:
    ADD R0, R0, #1
    BX LR         ; 返回 A
```

如果 B 自己还会执行 `BL C`，新的 `BL` 会覆盖 B 当前的 LR，因此 B 通常要先保存其返回 A 所需的 LR，或以其他正确方式安排控制流。

> 除 R0～R15，还有 xPSR、PRIMASK、BASEPRI、FAULTMASK、CONTROL 等**特殊寄存器**。不要误认为 Cortex-M7 只有 16 个物理寄存器，也不要把这些 CPU 寄存器等同于片内 SRAM。

## 4. 栈为什么能正确恢复？中途又压入其他数据怎么办

### 4.1 压栈的寄存器不需要单独的“寄存器专用栈”

`PUSH` 只是在**当前 SP 指向的 RAM 栈**里保存寄存器的数值。Cortex-M7 常用的栈模型是**满递减栈（Full Descending）**：压栈时地址向低处增长。

假设起始：

```text
SP = 0x20001000
R4 = 10, R5 = 20, LR = 0x08001235
```

执行：

```asm
PUSH {R4, R5, LR}
```

之后：

```text
较高地址
0x20001000    原 SP 位置（未由该 PUSH 写入）
0x20000FFC    LR = 0x08001235
0x20000FF8    R5 = 20
0x20000FF4    R4 = 10        <-- 新 SP
较低地址
```

一次 `PUSH` 保存了三个 32 位数，共 12 字节；新 SP 为 `0x20000FF4`。**低编号寄存器保存在较低地址**，排列规则由架构确定，不是汇编文本中的任意逐条执行顺序。

### 4.2 如果中间再保存 R6

```asm
PUSH {R4, R5, LR}   ; SP = 0x20000FF4
PUSH {R6}           ; SP = 0x20000FF0（新增 R6 在更低地址）
POP  {R6}           ; SP = 0x20000FF4（恢复到原栈顶）
POP  {R4, R5, PC}   ; 恢复 R4/R5，原 LR 的值被装入 PC，返回
```

关键是：**先进入栈的数据不被后来的压栈移动或打乱**；后压的数据占用更低地址，必须先释放，SP 才能重新指向原来的 R4。

错误示例：

```asm
PUSH {R4, R5, LR}
PUSH {R6}
POP  {R4, R5, PC}   ; 错误：SP 仍指向 R6
```

这不会让 CPU 自动“查找以前的 R4”。它只会从当前 SP 起的连续位置取值，导致寄存器错位，写入 PC 时甚至可能跳转到错误地址并触发异常。

> `POP` 后，相应 SRAM 字节中的旧内容可能仍留在物理内存里，但这些字节在**逻辑上**不再属于当前已占用的栈帧。

### 4.3 C 函数的栈帧：编译器管理成对分配/释放

下面是展示函数入口/出口的简化示意，20 字节空间只是示例：

```asm
my_function:
    PUSH {R4, R5, LR}     ; 保留寄存器；SP -= 12
    SUB  SP, SP, #20      ; 为局部变量/对齐预留空间；SP -= 20

    ; 函数主体，可能有其他运算和调用

    ADD  SP, SP, #20      ; 释放局部变量空间
    POP  {R4, R5, PC}    ; 恢复寄存器，并返回
```

如果进入时 SP 为 8 字节对齐，`12 + 20 = 32` 字节，调用边界仍可维持 8 字节对齐。实际函数会根据 ABI、优化和栈布局选择不同序言（prologue）/尾声（epilogue）。

**要点**：普通函数的栈帧不是“每个寄存器一块专用 SRAM”，而是当前任务/线程所使用的栈中的连续区域。

## 5. Caller-saved、Callee-saved、R9 平台相关的区别

设函数 A 调用函数 B：

| 类型 | 寄存器 | 谁保证旧值在 B 返回后还可用？ | B 是否可修改？ |
| --- | --- | --- | --- |
| **Caller-saved**（调用者保存） | R0～R3、R12 | **A**：如果要保留，A 自己想办法保存 | B 可以直接修改，通常不需要还原旧值 |
| **Callee-saved**（被调用者保存） | R4～R8、R10、R11 | **B**：若 B 使用并修改，必须在返回前恢复 | B 可以修改，但返回时这些寄存器须保持符合约定的原值 |
| **平台相关** | R9 | 由具体 ABI 的平台约定决定 | 依约定，不能脱离目标 ABI 一概而论 |

### 5.1 Caller-saved 的真实含义

- 并不是 A 每次调用前都要 `PUSH {R0}`。
- 只有 A 在调用后**还需要旧值**时，才有保存的必要。
- B 往往把函数参数放在 R0～R3 中接收，并把返回值放在 R0（或 ABI 指定的位置），自然会覆盖原值。

例如：

```c
int B(int x) { return x + 1; }
```

```asm
B:
    ADD R0, R0, #1    ; R0 输入 x，返回 x+1
    BX  LR
```

这不需要保存 R0，因为 B 的契约本来就是把结果返回在 R0。

### 5.2 Callee-saved 的真实含义

如果 B 想修改 R4：

```asm
B:
    PUSH {R4, LR}
    MOV  R4, R0
    ; ...使用 R4 进行计算...
    POP  {R4, PC}
```

B 必须使调用者能继续使用调用前的 R4。如果 B 从不改动 R4，就不必为了“形式上遵守规范”而压栈。

### 5.3 R9 的例外性

在 AAPCS32 中，R9 可由平台指定为：

- `SB`（Static Base，静态基址）；
- `TR`（Thread Register，线程相关寄存器）；
- 或在不需要特殊职责的平台上作为另一个 callee-saved 通用寄存器。

对常见 STM32H743 GNU Arm 裸机工程，R9 通常按被调用者保存通用寄存器使用；写手工汇编、移植 RTOS/运行库或特殊 ABI 时，应核对实际 ABI。

### 5.4 LR 的保存原因与 R4 不同

```asm
B:
    PUSH {R4, LR}
    MOV  R4, R0
    BL   C
    POP  {R4, PC}
```

- 保存 **R4**：因为 B 需要使用它，却必须向调用者保证它不变。
- 保存 **LR**：因为 `BL C` 会覆盖 LR，B 还需要原先“返回 A”的位置。
- 恢复到 **PC**：是把之前保存在栈中的返回地址用于分支返回，而不是“PC 也属于普通被调用者保存寄存器”。

## 6. 最容易困惑的一点：R0 既是参数又是返回值，何时恢复旧 R0？

**结论：如果调用者既要旧 R0，又要被调用函数返回的 R0，就必须在恢复旧 R0 之前先保存/使用返回值。** 被调用函数执行 `BX LR` 后，只是返回到调用者的下一条指令，并不会自动触发 `POP {R0}`。

### 6.1 两个值都要保留的完整教学例子

假设 A 内部需要保留旧值 100，同时调用 `B(10)` 得到 11，最后计算 100 + 11 = 111 作为 A 的返回值。

```asm
A:
    PUSH {R4, LR}       ; A 保存 R4 和自己的返回地址，8 字节
    MOV  R0, #100       ; 模拟 A 原本想保留的 R0 值
    PUSH {R0, R1}       ; 保存旧 R0；R1 只是示例用额外保存，保持 8B 对齐

    MOV  R0, #10        ; B 的参数写入 R0，覆盖 R0 原值
    BL   B              ; 返回时 R0 = 11
    MOV  R4, R0         ; 先把返回值 11 转存到 R4
    POP  {R0, R1}       ; 再恢复 A 原本的 R0 = 100
    ADD  R0, R0, R4     ; R0 = 100 + 11 = 111，作为 A 的返回值

    POP  {R4, PC}       ; 恢复调用 A 之前的 R4，按旧 LR 返回

B:
    ADD  R0, R0, #1     ; B(10) 的返回值 = 11
    BX   LR
```

步骤追踪：

| 时刻 | R0 | R4（A 内的临时用途） | 栈里保存的旧 R0 |
| --- | ---: | ---: | ---: |
| A 写入旧数据 | 100 | 未指定 | 尚未保存 |
| A 执行 `PUSH {R0, R1}` | 100 | 未指定 | 100 |
| A 为 B 传参 | 10 | 未指定 | 100 |
| B 返回 | **11** | 未指定 | 100 |
| `MOV R4, R0` | 11 | **11** | 100 |
| `POP {R0, R1}` | **100** | 11 | 已恢复 |
| `ADD R0, R0, R4` | **111** | 11 | 已恢复 |

本例是为解释保存顺序而构造的自洽、可理解的汇编流程；不代表编译器必须按此方式实现 C 代码。R1 的保存并非 ABI 强制，只是便于保持该示例的 8 字节调用栈对齐。

### 6.2 更常见的情况：根本不需要保存旧 R0

```c
int B(int x) { return x + 1; }
int A(void) { return B(10) * 2; }
```

调用 B 后，A 只需要结果 11，而不需要进入 B 前 R0 的旧值，因此可以直接利用返回值：

```asm
    MOV R0, #10
    BL  B           ; B 返回 R0 = 11
    LSL R0, R0, #1  ; R0 = 22
```

这一段仅展示相关部分；完整非叶子函数还必须正确处理 A 自己的返回地址与栈对齐。

### 6.3 编译器常采用更经济的方案

如果某个值要跨多次函数调用长期保留，编译器可能直接把它放入 R4～R11 这类 callee-saved 寄存器，减少每次调用前后反复保存 R0 的次数。

**区分三个动作**：

1. **B 写返回值到 R0**：这是 ABI 的返回值约定。
2. **`BX LR` 返回 A**：只是恢复控制流，不会自行替 A 恢复旧 R0。
3. **A 的后续指令**：决定先使用/转存返回值，还是恢复旧值，或根本不用恢复。

## 7. DTCM（0x20000000）到底能不能做堆和栈？

**能。** STM32H743 的 `0x20000000` 是 **DTCM RAM** 起始地址，不是 ITCM；DTCM 是 128 KB 的真实片内 SRAM，适合低延迟、可预测的栈访问。

```text
DTCM 有效地址范围：0x20000000 ~ 0x2001FFFF
DTCM 末尾后一个地址：0x20020000
```

栈向低地址增长，因此可令**初始 SP** 位于末尾后一地址（前提是这片区域已合理分配，不和其他数据冲突）：

```ld
/* 仅示意 .ld 的局部设置 */
MEMORY {
    DTCMRAM (xrw) : ORIGIN = 0x20000000, LENGTH = 128K
}
_estack = ORIGIN(DTCMRAM) + LENGTH(DTCMRAM); /* 0x20020000 */
```

典型 Cortex-M 启动向量表的第一个字存放初始 MSP：

```asm
.word _estack
.word Reset_Handler
```

若 SP 初值为 `0x20020000`，执行 `PUSH {R4, R5, LR}` 后：

```text
SP = 0x2001FFF4
R4 保存到 0x2001FFF4
R5 保存到 0x2001FFF8
LR 保存到 0x2001FFFC
```

**重要边界**：

- `_estack` 指定栈顶地址，**并不自动保证**整个 DTCM 都保留给栈，也不负责检测堆栈碰撞。
- 堆（Heap）是由内存分配器管理的区域，不是 SP 的另一种叫法；`malloc()` 的堆空间取决于链接脚本和 `_sbrk` / 运行库实现。FreeRTOS 的动态内存方案另有自己的分配机制。
- SP 可以指向 DTCM，也可以指向其他合法、可写、满足栈对齐和访问权限的 SRAM 区域；`PUSH`/`POP` 本身不关心底层 RAM 块名字。
- **异常栈与任务栈**：Handler mode 使用 MSP；若异常发生时 Thread mode 使用 PSP，硬件入栈的异常帧通常保存到被打断线程使用的 PSP，然后异常处理程序运行在 MSP 上。不能简单说“发生中断一定把现场压到 MSP”。

## 8. 把一个常见的 H743 反汇编片段逐行读懂

先前讨论过的片段：

```asm
bl   HAL_GPIO_TogglePin
ldr  r3, [pc, #24]
ldr  r3, [r3, #0]
adds r3, #1
str  r3, [r2, #0]
```

| 指令 | 真实操作 |
| --- | --- |
| `BL HAL_GPIO_TogglePin` | 跳转调用，LR 记录返回位置 |
| `LDR R3, [PC, #24]` | 从 PC 相对地址位置读取一个 32 位字（常见于常量池） |
| `LDR R3, [R3, #0]` | 将刚取出的值作为内存地址，读取该地址的数据 |
| `ADDS R3, #1` | 把 R3 加 1，并更新相关条件标志 |
| `STR R3, [R2, #0]` | 将 R3 写到 **R2 指向的地址**，不是自动写回刚才 R3 读过的地址 |

仅凭这五条指令，**不能断言**最后一定写回某个指定的全局变量：还需要查看 R2 当时保存的地址，以及前后的指令、反汇编地址和符号表。

## 9. 复习清单：怎样判断自己是否真的理解了

- [ ] 能区分 `MOV R0, R1`、`LDR R0, [R1]`、`STR R0, [R1]`。
- [ ] 理解 `[]` 是内存寻址、`{}` 是寄存器列表、`#` 是立即数。
- [ ] 能根据 SP 初始值，算出 `PUSH {R4,R5,LR}` 后的新 SP 和每个寄存器的存放地址。
- [ ] 知道“中途 PUSH 了其他数据”时，必须先恢复/释放新增内容，再 POP 旧寄存器。
- [ ] 能区分 R0～R3 传参/返回、R4～R11 的保存义务、LR 返回地址、PC 程序控制、SP 栈顶。
- [ ] 能准确说出 Caller-saved 与 Callee-saved 的**责任归属**，而不是误以为每次函数调用都必定压栈。
- [ ] 知道 R0 返回值与旧 R0 可能冲突，调用者须先转存结果，再恢复旧值；无需旧值则不用保存。
- [ ] 知道 0x20000000 是 DTCM，并能解释为什么 SP 可以设置到有效 DTCM 区域顶端。
- [ ] 在 CubeIDE Disassembly 中能跟踪 `BL`、`BX LR`、`PUSH`、`POP` 以及调试器当前 R0、LR、SP。
