# STM32H743 寄存器与内存布局

从 `DBGMCU->IDCODE` 的 C 语言语法出发，理解内存映射寄存器、`volatile`、链接脚本和启动初始化。

> 适用环境为 STM32H743、ARM GCC 和常见 STM32CubeIDE 裸机工程。根据 2026 年 11 月 4–5 日的讨论记录《2026_11_4讨论_bss.html》整理。

:::tip 要点
设备头文件用“地址 + 结构体指针”描述硬件寄存器；`volatile` 约束编译器的访问优化；编译器生成输入段，链接脚本确定这些段在 Flash/RAM 中的布局，启动代码负责复制 `.data`、清零 `.bss`。
:::

## DBGMCU 寄存器访问语法

```c
#define DBGMCU_BASE  (0x5C001000UL)
#define DBGMCU       ((DBGMCU_TypeDef *) DBGMCU_BASE)

g_dbg_idcode = DBGMCU->IDCODE;
```

| 语法 | 作用 | 理解方式 |
| --- | --- | --- |
| `#define` | 预处理宏定义 | 在预处理阶段做标记替换，本身不创建变量。 |
| `0x` | 十六进制前缀 | `0x5C001000` 是一个整数形式的地址值。 |
| `UL` | 无符号 long 整数后缀 | 在常见 32 位 ARM GCC 工具链中为 32 位 unsigned long。 |
| `DBGMCU_TypeDef *` | 结构体指针类型 | 指向具有 DBGMCU 寄存器布局的对象。 |
| `(DBGMCU_TypeDef *)` | 强制类型转换 | 让编译器按结构体布局解释给定地址。 |
| `->` | 通过指针访问成员 | `p->IDCODE` 等价于 `(*p).IDCODE`。 |

宏展开以后：

```c
g_dbg_idcode = ((DBGMCU_TypeDef *)0x5C001000UL)->IDCODE;
```

对于 STM32H743，此处的 `IDCODE` 位于 DBGMCU 寄存器块起始偏移 `0x00`，因此读取的是相应的内存映射外设寄存器，而不是普通 RAM 变量。

:::tip 要点
注意：**宏定义和指针类型转换本身不产生寄存器读取**。执行成员读取表达式（如 `DBGMCU->IDCODE`）时，才发生访问。具体寄存器布局以对应芯片的 CMSIS 头文件、参考手册为准。
:::

### 结构体为何能够对应寄存器地址？

```c
/* 教学示意：不是 H743 的完整 DBGMCU_TypeDef */
typedef struct {
    volatile uint32_t IDCODE;  // 偏移 0x00
    volatile uint32_t CR;      // 偏移 0x04，仅作布局示例
} ExampleDBG_TypeDef;
```

结构体成员按定义产生偏移；外设映射地址提供结构体起点；C 语言的成员访问语法把两者结合起来。这就是 CMSIS 寄存器级编程常见的实现方式。

## 寄存器位域与汇编读改写 {#register-fields}

寄存器窗口中缩进的 WT、WB、RA 等，通常是同一个寄存器内部的**位域（bit field）**，不是又分配了独立硬件地址的“小寄存器”。

### 调试器位域标记 `[31:1]`

在原记录的调试器视图中，冒号后的数字表示**位宽**，因此 `[31:1]` 表示从 bit 31 开始的 1 位字段；`[13:15]` 表示从 bit 13 开始、长度 15 位。它不是通常文档写法的 `[31:1]`（bit31 到 bit1）。

| 界面字段 | 硬件含义 |
| --- | --- |
| `CCSIDR` | Cache Size ID Register：描述某一层级 Cache 的结构与能力。 |
| `WT / WB` | 是否支持 Write-through / Write-back 缓存策略。 |
| `RA / WA` | 是否支持 Read-allocate / Write-allocate 策略。 |
| `NS / A / LS` | Cache 的组数、相联度与缓存行大小的编码字段，通常要按架构定义换算，不是直接把原值当字节数。 |

:::tip 要点
**不要混淆地址与值：**`0xE000ED80` 是 Cortex-M7 的 CCSIDR 寄存器地址；调试器如果在地址栏显示它，不等于寄存器内容就是该数值。
:::

以后你看到 `RCC_CFGR`、`GPIOB_MODER`、`FDCAN_RXF0C`，可以按照同样思路理解：**地址 → 整个寄存器 → 字段所在位 → 编码值 → 对硬件行为的影响**。

### 从 ARM 汇编追踪写回地址

```asm
bl   HAL_GPIO_TogglePin  ; 调用函数，可能翻转 LED
ldr  r3, [pc, #24]       ; 从 PC 相对位置加载一个字（可能是地址）
ldr  r3, [r3, #0]       ; 读取该地址中的值
adds r3, #1             ; 对寄存器中的值 +1
str  r3, [r2, #0]       ; 写到 r2 指向的地址！
```

两条 ldr 和一条 adds 依次加载地址、读取旧值和加 1。但最后写回用的是 `r2` 而不是 `r3` 原地址，**必须确认 r2 当时的值**，才能断言写回的确是同一个 `g_heartbeat`。这就是看汇编时不能只根据变量注释猜测程序行为的原因。

## volatile 与寄存器访问

`volatile` 告诉编译器：对该对象的访问具有必须保留的可观察副作用，不能仅凭普通变量的优化假设擅自省略、合并访问。

```c
volatile uint32_t status;
uint32_t x = status;  // 第一次读取
uint32_t y = status;  // 第二次读取仍需保留

while ((USART1->ISR & USART_ISR_RXNE_RXFNE) == 0U) {
    // 反复读取 USART 状态，而不是一直沿用第一次读到的旧值
}
```

### 四条实用规则

1. **读取：**不同的必要读取不能因数值“看似没变”就被折叠成一次。
2. **写入：**对 volatile 对象有意义的写操作不能仅因后来覆盖而被删掉。
3. **顺序：**须遵守 C 语言对 volatile 访问的求值顺序要求，但不是通用内存屏障。
4. **原子性：**`REG++` 或 `REG |= MASK` 仍可能包含“读—修改—写”多个步骤。

:::warning 注意
**对话中需要特别纠正的口语化理解：**“每次从 RAM 重新读，不能从寄存器偷懒”大方向接近，但更准确是“每次按语义访问指定对象地址，不能把之前留在 CPU 通用寄存器的旧值直接当作新读取”。这不保证绕过 CPU D-Cache，也不能自动解决 DMA 缓冲区的缓存一致性。
:::

硬件外设寄存器、CPU 通用寄存器、RAM、D-Cache 是四个不同概念。对 STM32H743 来说，尤其要把 DMA 可访问性、Cache 维护、MPU 内存属性与 `volatile` 分开考虑。

## .data 与 .bss 的初始化

| 对比 | `.data` | `.bss` |
| --- | --- | --- |
| 典型内容 | 有非零初始值的可读写全局/静态变量 | 零初始化的全局/静态变量 |
| 运行位置 | RAM（典型裸机布局） | RAM（典型裸机布局） |
| 程序镜像 | 通常需要在 Flash 保存初始值 | 通常仅记录空间大小，无需保存一串零 |
| 启动动作 | 从 Flash 将初始值复制到 RAM | 将对应 RAM 清零 |

```c
int count;                 // 通常 .bss
static int error_flag;     // 通常 .bss
int retries = 0;           // 通常 .bss
int baudrate = 115200;     // 通常 .data

uint8_t rx_buffer[4096];   // 通常 .bss，占 4096 字节 RAM
```

**BSS 全称：***Block Started by Symbol*（历史上的汇编伪指令名称）。它的现代工程含义可以直接记为“运行时预留、启动时通常清零的静态存储空间”。

对于上述 `rx_buffer`，程序通常要给它分配 4 KiB RAM，却无需为这 4 KiB 内容在 Flash 中保存同样长度的零数据。

:::tip 要点
这里说的是**通常**：编译器优化、链接脚本和显式节属性可能改变变量的具体去向。局部自动变量通常属于栈或被优化到寄存器，不因为“没初始化”就自动属于 `.bss`。
:::

## STM32H743 存储区域与链接脚本

必须区分 **Section（逻辑段）** 和 **Memory Region（存储区域）**。

| 典型存储区域 | 起始地址 | 备注 |
| --- | --- | --- |
| 内部 Flash | `0x08000000` | 通常放程序代码、只读数据及 .data 初始值 |
| DTCM RAM | `0x20000000` | 适合内核快速访问；普通 DMA1/DMA2 不能直接访问 |
| AXI SRAM（D1） | `0x24000000` | H743 常用大容量 SRAM 区域 |
| SRAM1（D2） | `0x30000000` | D2 域 SRAM |
| SRAM4（D3） | `0x38000000` | D3 域 SRAM |

这些是地址示例，具体容量及 DMA/总线访问条件应核对实际 H743 型号手册与工程配置。`.bss` 不是 DTCM 的别名，`.data` 也不是 AXI SRAM 的别名。

### 链接脚本由谁产生？

- STM32CubeIDE 创建工程时通常生成或提供一个 `.ld` 文件。
- 开发者可以修改、替换或完全手写它；链接器在**链接阶段**读取脚本。
- 不等于“每次编译一个 `.c` 文件都重新生成链接脚本”。

```text
/* 简化示例：定义可用的存储区域 */
MEMORY
{
    FLASH  (rx)  : ORIGIN = 0x08000000, LENGTH = 2048K
    RAM_D1 (xrw) : ORIGIN = 0x24000000, LENGTH = 512K
}

/* 简化示例：指定输出段的运行位置和加载位置 */
.data :
{
    *(.data)
    *(.data*)
} >RAM_D1 AT>FLASH

.bss :
{
    *(.bss)
    *(.bss*)
} >RAM_D1
```

:::tip 要点
`>RAM_D1` 决定段的**运行地址**；`AT>FLASH` 决定 `.data` 初始化内容的**加载/存储位置**。示例为教学片段，并非可独立使用的完整链接脚本。
:::

更复杂的工程会按 DMA、Cache、实时性等需求将缓冲区单独分节，例如 `.dma_buffer`，并在链接脚本中指定目标 SRAM 区域。

## 从编译到 main()

C 源文件 `.c` → 编译为目标文件 `.o` → 链接脚本参与布局 `.ld` → 生成程序镜像 `.elf/.bin`

上电进入 `Reset_Handler` → 复制 `.data` Flash → RAM → 清零 `.bss` RAM 内存 → 完成运行库初始化 调用 `main()`

具体启动顺序会因启动文件、C/C++ 运行库、系统初始化代码而变化。STM32 工程中可检查：

- `startup_stm32h743xx.s`：复位入口和早期初始化。
- `*.ld`：`MEMORY`、`SECTIONS`、`.data`、`.bss`。
- `*.map`：编译后每个段和符号的实际地址、大小。

## 与传统 8051 的地址空间对照

两者都涉及内存划分，但**划分维度不同**：传统 8051 / Keil C51 的 `data/idata/xdata/code` 更强调地址空间和寻址方法；STM32 的 `.data/.bss/.text` 更强调程序段的内容和初始化语义。

| 8051 / Keil C51 | 大致用途 | STM32 中的理解 |
| --- | --- | --- |
| `code` | 程序存储器地址空间 | 程序常见放在 Flash 的 `.text`；只读常量通常在 `.rodata` |
| `data` | 片内低 128 字节直接寻址数据空间 | 不等于 STM32 的 `.data` 段 |
| `idata` | 内部间接寻址的数据空间 | 无直接同名对应段 |
| `xdata` | 外部/扩展数据地址空间 | 无直接同名对应段 |
| `bdata` | 支持位寻址的内部 RAM 数据区域 | 无直接同名对应段 |
| `SFR` | 特殊功能寄存器 | 概念上可类比 STM32 的内存映射外设寄存器 |

**关键区别：**经典 8051 有明显区分的程序/数据地址空间；STM32H743 将 Flash、RAM、外设等映射到统一的 32 位地址空间，但内部仍有不同的总线和存储器接口。

## 工程源码核对清单

1. 在设备头文件中搜索 `DBGMCU_BASE`、`DBGMCU_TypeDef`，确认基地址和寄存器偏移。
2. 查 `__IO` 的定义，理解它通常与 `volatile` 的关系。
3. 打开链接脚本，找 `MEMORY`、`.data`、`.bss` 和栈堆配置。
4. 在启动文件中找 `Reset_Handler`，对应初始化指针/区间符号。
5. 打开 `.map` 文件，确认实际变量属于哪个段、地址是多少。
6. 为 CAN/FDCAN 网关准备 DMA 缓冲区时，再独立核查 SRAM 可访问性与 Cache 策略。

**问题现实性：**上述知识直接用于 STM32H743 的底层驱动、CAN 网关、Bootloader、DSP 缓冲区和资源优化，属于必要的嵌入式基础。**技术结论置信度：**高；具体设备布局以实际芯片料号、参考手册和工程文件为准。
